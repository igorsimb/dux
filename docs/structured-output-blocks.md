# Structured output blocks for SQL result tables

The chat UI used to rely on the model to turn SQL results into markdown tables. That made query answers easier to read,
but it kept database rows inside generated prose. The frontend could only treat those rows as text, and the model could
accidentally omit, reshape, or invent table cells while preparing the final answer.

Structured output blocks move table rendering to a safer boundary:

- the LLM writes Russian commentary and chooses where result tables belong in the answer
- the backend owns SQL result rows, column metadata, row counts, and truncation
- the UI renders each final block with the renderer that matches its type

This matters because the assistant is a guarded SQL assistant. The visible table should reflect actual SQL execution,
not a probabilistic rewrite of the rows.

## How it works

The current flow is complete-block rendering, not progressive table streaming:

```text
User question
-> LangGraph agent runs the guarded SQL loop
-> model validates SQL with validate_sql
-> model executes SQL with execute_validated_sql(validated_id)
-> backend converts real SQL rows and execution facts into DataTableBlock objects in sql_result_table_blocks
-> model returns AgentCommentaryResponse with commentary and data_table_placeholder blocks only
-> model may attach explanatory table notes to placeholders
-> backend resolves placeholders against sql_result_table_blocks with build_final_response_blocks(...)
-> backend filters answer details by the current user's permissions
-> backend sends final AgentFinalResponse blocks to the Django/DataStar UI
-> live response renders through Django partials
-> same-tab restore rebuilds the DOM from permission-filtered raw block JSON in sessionStorage
```

The important invariant is simple: **table rows are never generated by the LLM**. The model may explain the data and
place table slots in the answer, but `DataTableBlock.rows` comes from backend SQL execution.

The same boundary applies to answer details. Table rows, columns, counts, source, table names, validation identity,
dialect, and raw SQL are backend-owned. The model can only add short explanatory notes to the matched table placeholder.

## Schema roles

The structured block models live in `ai/ai_utils/structured_output_blocks.py`.

### `AgentCommentaryResponse`

This is the LLM-facing structured response configured on the agent. It can contain only:

- `CommentaryBlock`
- `DataTablePlaceholderBlock`

It cannot contain `DataTableBlock` objects or SQL rows. This keeps the model out of the table-serialization path.

### `DataTablePlaceholderBlock`

This is a model-produced layout slot with `type="data_table_placeholder"`. It can include an optional `title`, but it
never includes columns or rows.

It can also include optional `notes`. These are model-supplied user-facing explanations for the matched table, such as
`Период`, `Фильтр`, `Метрика`, or `Интерпретация`. They are attached under `details.notes` only after the backend
resolves the placeholder to a real `DataTableBlock`.

During final assembly, the backend replaces placeholders positionally with backend-owned SQL result blocks.

### `AgentFinalResponse`

This is the backend-assembled response rendered to the user. It can contain only:

- `CommentaryBlock`
- `DataTableBlock`

By the time the UI sees final blocks, there are no placeholders left.

### `DataTableBlock`

This is the backend-produced table block. It contains:

- `columns`: backend-owned ordered column metadata with a key, label, and inferred simple type
- `rows`: backend-owned normalized SQL result rows
- `meta.row_count`: backend-owned total rows returned by execution
- `meta.rendered_row_count`: backend-owned rows included in the rendered block
- `meta.truncated`: whether rendering was limited
- `details.facts`: backend-owned execution facts, including `source_id`, `dialect`, `validated_id`, `tables`, and
  formatted `raw_sql`
- `details.notes`: optional model-supplied explanatory notes attached from the matched placeholder

`build_data_table_block(...)` uses `DEFAULT_SQL_RESULT_ROW_LIMIT = 50` unless a smaller explicit query limit applies.

Raw SQL in `details.facts.raw_sql` is formatted with the same backend formatter used for SQL execution logs. The UI shows
it inside the nested `Показать SQL` section when permitted, and authorized users can copy it from the table details panel.

## Placeholder resolution

Final block assembly happens in `ai/ai_utils/streaming.py` through `build_final_response_blocks(...)`.

Resolution is positional:

1. Read `sql_result_blocks` from graph state.
2. Validate each stored block as a `DataTableBlock`.
3. Walk the LLM's `AgentCommentaryResponse.blocks` in order.
4. Keep `commentary` blocks as-is.
5. Replace each `data_table_placeholder` with the next valid backend-owned table block.
6. If the placeholder has a title and the backend table does not, copy that title onto the rendered table block.
7. Append any extra backend-owned table blocks that were not matched by placeholders.

If a placeholder includes `notes`, those notes are copied to the matched table's `details.notes`. Notes are rendered after
backend-owned rows in the `Детали` panel. Notes whose labels collide with backend-owned detail labels are filtered out:
`Источник`, `Таблицы`, `Строк показано`, and `SQL`.

`ChatAgentState` declares `sql_result_blocks` in `ai/ai_utils/agent_state.py`. That declaration is required so LangGraph
preserves table blocks produced by the SQL tool until final response assembly.

Fresh user turns start with `sql_result_blocks: []`, which prevents a table from an earlier turn from leaking into a
later answer.

## Error and edge-case behavior

Empty SQL results are valid tables. A query that returns no rows still produces a `DataTableBlock` with empty `rows`,
zero row counts, and `truncated=false`. The UI renders the normal empty-table message instead of treating it as a
missing table.

Database errors stay in the tool/LLM correction loop. If SQL execution fails, the error is returned through the tool
path so the model can correct the query according to the existing retry behavior. It is not converted into a table
block.

Unmatched placeholders are skipped. If the LLM emits a `data_table_placeholder` and there is no matching backend-owned
table block, `build_final_response_blocks(...)` logs a warning and drops that placeholder instead of showing a confusing
missing-table error to the user.

Malformed `sql_result_blocks` are skipped. If graph state contains a block that does not validate as `DataTableBlock`,
final assembly logs a warning and continues with the remaining valid blocks. A malformed stored block should not crash
final rendering.

SQL cell values are serialized safely for the HTML attribute that stores raw blocks. `ai/ai_utils/ui.py` uses
`json.dumps(..., default=str)` for `data-chat-blocks`, so values such as `Decimal` do not break response rendering.

## Rendering and restore behavior

Live structured responses are server-rendered in `ai/ai_utils/ui.py`:

- `make_robot_blocks_html(...)` wraps the assistant message and stores raw final blocks in `data-chat-blocks`
- `format_structured_block_html(...)` dispatches each block by type
- `commentary` uses `ai/partials/commentary_block.html#commentary-block`
- `data_table` uses `ai/partials/data_table_block.html#data-table-block`

The partial templates live under `ai/templates/ai/partials/`.

Commentary still uses the client-side markdown path in `ai/templates/ai/ai_main.html`. The template stores the raw
commentary text and the browser renders it with `marked` plus `DOMPurify`, the same approach used for markdown-only
assistant text.

Data tables are rendered by the server for live responses. On same-tab restore, the browser does not reuse saved HTML.
Instead, `sessionStorage` stores raw final `blocks` JSON, and `ai/templates/ai/ai_main.html` rebuilds commentary and
table DOM nodes from that JSON. This keeps restore tied to the block contract instead of a snapshot of old markup.

Each `data_table` block may render one local collapsed `Детали` panel. The backend-owned visible rows are:

- `Источник`
- `Таблицы`
- `Строк показано`
- nested `Показать SQL`, when raw SQL is permitted

Model notes from `details.notes` render after those backend-owned rows.

Details are permission-filtered before both HTML rendering and `data-chat-blocks` serialization:

- `core.view_answer_notes` shows model notes and non-SQL backend facts.
- `core.view_raw_sql` shows raw SQL and non-SQL backend facts.
- Users with neither permission receive no details panel, and restricted details are omitted from both HTML and
  `data-chat-blocks`.

The default permission groups are migration-created in `core/migrations/0002_answer_details_permissions.py`:

- `AI answer notes viewers`
- `AI raw SQL viewers`

Same-tab restore uses the saved, permission-filtered block JSON, so restored `Детали` panels match what the server was
allowed to send for that user.

Chatlogs remain plain visible text. `build_blocks_visible_text(...)` keeps commentary text and writes each table as a
compact summary such as `[Таблица: ..., строк показано: ... из ...]`.

Structured JSON chunks from the model are suppressed during token streaming. Users should not see raw
`{"blocks": ...}` payloads while the final structured response is being assembled, including pretty-printed JSON with
leading whitespace before `"blocks"`.

## Why backend-owned rows matter

The model still needs to see SQL results so it can explain them, but the visible table should not be reconstructed from
natural language. Keeping rows backend-owned gives the app a stable source of truth for:

- exact cell values returned by the database
- null and missing-value handling
- row-count and truncation metadata
- future table behavior such as sorting, filtering, export, or progressive updates

It also reduces prompt pressure. The model no longer has to spend final-answer tokens formatting large markdown tables,
and the frontend no longer has to parse table data out of prose.

## Where to look in the code

The main implementation files are:

- `ai/ai_utils/structured_output_blocks.py` - Pydantic block contracts, row normalization, type inference, table
  block creation, and answer detail schemas
- `ai/ai_utils/agent_state.py` - `ChatAgentState`, including `sql_result_table_blocks`
- `ai/ai_utils/streaming.py` - structured response extraction, JSON-token suppression, fresh-turn state reset, and
  placeholder resolution, including placeholder note attachment
- `ai/ai_utils/ui.py` - server-side block HTML rendering, answer detail permission projection, raw block JSON storage,
  reserved note-label filtering, and chatlog visible-text conversion
- `ai/ai_tools.py` - SQL execution and creation of backend-owned `DataTableBlock` payloads with execution facts
- `ai/views.py` - SSE handling for final structured block events and per-user answer detail permissions
- `ai/templates/ai/ai_main.html` - client-side markdown rendering, transcript persistence, same-tab block restore, and
  restored details/SQL copy UI
- `ai/templates/ai/partials/commentary_block.html` - commentary partial
- `ai/templates/ai/partials/data_table_block.html` - data table partial and live `Детали` panel
- `core/models.py` - answer detail permission declarations
- `core/migrations/0002_answer_details_permissions.py` - default answer detail groups

## Future work

Progressive table rendering is not implemented yet. The current UI renders complete `data_table` blocks after backend
assembly.

The planned future shape is:

- `data_table_start`
- row batch append events
- `data_table_done`

That work should preserve the same core invariant: visible table rows come from backend SQL execution, not from the LLM.
